## What this repo is

The container images the jay-withers apps build from and deploy with: `python-app` and `python-app-builder` (the runtime and builder bases for every Python app) and `placeholder` (what an app's Terraform first creates its container app with). Each is defined under `images/<name>/Dockerfile` and published to the GitHub Container Registry (`ghcr.io/jay-withers/dev-containers/<name>`). There is no application code.

It used to build VS Code dev container images too (`base`, `terraform`, `k8s`). Those are retired: every repo now pins its tools in `mise.toml` (jay-withers/toolchain sets a machine up), and the shared workflows install from it in CI. Don't reintroduce a dev-container image here; a tool every repo needs goes in toolchain's global mise config, and a repo-specific one in that repo's `mise.toml`. Their old GHCR packages are no longer pruned or scanned, since both scripts discover images from `images/`.

Common tasks are wrapped in the `Makefile` (run `make help` to list them):

```sh
make setup   # mise install (mise.toml), then install the pre-commit git hooks
make lint    # run all pre-commit hooks against every file (the standard way to validate changes)
make build   # build every image locally (python-app, python-app-builder, placeholder)
make smoke-test  # run each image's smoke tests against the locally built images
```

Two scheduled maintenance tasks are also wrapped: `make prune-packages` (GHCR retention, dry-runs by default) and `make scan-images` (vulnerability report on the published images).

Individual image builds are also available (`make build-python-app`, `make build-python-app-builder`, `make build-placeholder`). The `lint`/`setup` targets wrap `pre-commit`, which picks up `.pre-commit-config.yaml` from the repo root automatically.

## Architecture

### Images

Images form a root + leaf hierarchy under `images/`:

- **`images/python-app/Dockerfile`** — the runtime base the Python apps on the shared Container Apps environment build `FROM` (gym-log, finances, career, repo-agent, market-agent). It is `python:3.14-slim-bookworm` pinned by digest, with `apt-get upgrade`, pip removed, a non-root uid 10001 user and `/app/.venv/bin` on `PATH`. A root image. The `REBUILD` build arg, set to the version by `cd-publish`, exists only to force the apt layer past the GHA cache on every publish, the weekly rebuild included. It sets this repo's `org.opencontainers.image.source` label, which every app image inherits unless it sets its own.
- **`images/placeholder/Dockerfile`** — the image an app's Terraform creates its container app with before the app's first release exists. A static Go server (`main.go`, built in a `golang` stage) on `alpine` pinned by digest, with `apk upgrade` (behind the same `REBUILD` arg) and non-root uid 10001. It answers 200 on **every** path on `$PORT` (default 8080), because the app's probes point at the app's own health path, which it cannot know. A root image with no leaves. `ENTRYPOINT`, not `CMD`, because apps pass `args` (`serve`) that Terraform doesn't ignore, and args replace a CMD; the server ignores them. Inside a Container Apps job (`CONTAINER_APP_JOB_NAME` set) it exits 0 at once instead of serving until the replica timeout. `scripts/smoke-test.sh` clears the entrypoint (`--entrypoint ''`) and runs each image's checks in bash only where the image has it, since Alpine has none.
- **`images/python-app-builder/Dockerfile`** — `FROM` python-app (via `BASE_IMAGE`). Adds uv and goes back to root. It exists as a separate image so an app's builder and runtime stages share one interpreter by construction: a venv only works under the minor version that built it.

Root images are listed in the `roots` matrices and leaves in the `leaves` matrices, where each leaf names its `parent` root. To add a new image, create `images/<name>/Dockerfile` and `images/<name>/smoke-tests` listing what it adds, then add it to the matching matrices in `cd-publish.yml` (`roots`+`roots-merge`, or `leaves`+`leaves-merge` with a `parent` entry) and in `ci-container-build.yml`. The smoke-test step itself needs no change — it reads the image's own list.

### Smoke tests

Each image declares the commands that prove its tooling works in **`images/<name>/smoke-tests`**: one shell command per line, `#` comments allowed. **`scripts/smoke-test.sh`** runs them inside the built image (a single `docker run` per image, `set -e`, output left visible since the printed versions are half the value when a wrong-architecture binary is the problem), and `make smoke-test` wraps it. `ci-container-build.yml` calls the same script, so CI and local runs can't drift.

The list lives beside the Dockerfile that installs the tools rather than in the workflow, so adding a tool means editing two files in one directory. Each image lists **only what it adds** — a leaf never re-tests what its parent provides — because each image is smoke-tested in the job that builds it, which is what makes a failure name the image that actually broke. Images and their lists are both discovered from `images/`, so a new image needs no change to the script or the workflow step. A missing `smoke-tests` file is an error rather than a silent pass. `ARCH=<arch>` additionally asserts the image reports that architecture before running anything, which is how a wrong-asset download gets caught; CI sets it from the build matrix.

### Architecture handling

Every image is published as a multi-arch manifest covering `linux/amd64` and `linux/arm64`, each architecture built on a native runner. The bases are pulled by digest (multi-arch indexes, so each runner resolves its own architecture), placeholder's Go server is compiled for `TARGETARCH`, and uv is copied from Astral's multi-arch image. `ARCH=<arch>` in the smoke test asserts the result.

### Pre-commit configuration

This repo's own hooks live in **`.pre-commit-config.yaml`** at the repo root — secret scanning, workflow/config linting, commit-message validation, plus the standard whitespace/format hooks. Hook revisions are frozen with a comment showing the upstream tag; Renovate keeps these updated automatically. The tools that run them (python, pre-commit, shellcheck) are pinned in **`mise.toml`**, and `make setup` installs them.

### Dependency pinning and updates

Base images (`FROM` and `COPY --from`) are pinned by tag and digest. **`renovate.json`** extends the shared [`jay-withers/renovate`](https://github.com/jay-withers/renovate) preset, which bumps those, the GitHub Actions pins, the pre-commit hook revisions and `mise.toml`. The OS packages inside the images are deliberately unpinned and upgraded on every publish instead (`REBUILD`). All Renovate PRs are auto-approved and auto-merged (squash) once CI passes.

### Commit messages

Commits must follow [Conventional Commits](https://www.conventionalcommits.org/). The commitlint hook (`commitlint.config.js`) enforces this at the `commit-msg` stage. The `no-commit-to-branch` hook blocks direct commits to `main`.

### CI

- **`.github/workflows/ci-pre-commit.yml`** — runs on PRs to `main`. Installs tools then runs `pre-commit run --all-files`. The `no-commit-to-branch` hook is skipped in CI via `SKIP=no-commit-to-branch`.
- **`.github/workflows/ci-container-build.yml`** — runs on PRs that change `images/**`. Builds the root images (python-app, placeholder) for `linux/amd64` and `linux/arm64`, each on a native runner of that architecture (`ubuntu-24.04` and `ubuntu-24.04-arm`), then builds the leaf (python-app-builder) `FROM` the matching per-arch parent. Every image is smoke-tested via `scripts/smoke-test.sh` in the job that builds it, on both architectures — so a root is proven before anything is built `FROM` it (the job loads as well as pushes, to run the image it just built), and the leaf job covers only its own additions. Because the leaf jobs run on different runners than the root jobs, each root is pushed to GHCR under a throwaway `pr-<run_id>-<arch>` tag; no release tag is published.
- **`.github/workflows/cd-tag.yml`** — runs on merge to `main`. Bumps the semver tag, then calls `cd-publish.yml` (reusable workflow) for the new version. Guarded so publish only runs when a tag was actually created.
- **`.github/workflows/cd-publish.yml`** — reusable (`workflow_call`) and manual (`workflow_dispatch`). Checks out the given tag, then runs five job stages: `roots` builds each root image per architecture on its native runner and pushes **by digest** with no tag; `roots-merge` combines those digests into one multi-arch manifest tagged with the version, reads it back from the registry to confirm it lists both `linux/amd64` and `linux/arm64`, and only then points `latest` at that exact digest — so a single-arch publish fails with `latest` untouched and before any leaf builds `FROM` it (the version tag is left single-arch; re-run against the same tag once fixed); `leaves` does the same per architecture for `python-app-builder`, referencing its freshly merged multi-arch parent at the same version (so each runner resolves its own architecture); `leaves-merge` publishes a multi-arch manifest per leaf image, with the same check before `latest` moves; finally `scan` calls `cd-scan.yml` for the version just published. Per-architecture digests travel between jobs as artifacts, since that is the only way to pass a value out of one matrix leg. They are named `digests-<image>--<arch>`, and the `--` is load-bearing: with a single `-`, the merge job's `digests-python-app-*` pattern would also pull in python-app-builder's digests. Re-runnable against an existing tag without minting a new version. The `scan` job gates nothing — everything is published before it starts, so a failure there is a failed report, not a failed release.
- **`.github/workflows/cd-scan.yml`** — reusable (`workflow_call`, invoked as the last job of `cd-publish` against the version just published) and manual (`workflow_dispatch`, to scan any published tag). Scanning at publish time rather than on a schedule ties each report to an exact immutable tag instead of whatever `latest` pointed at when a timer fired, and covers mid-week releases; `cd-weekly` still guarantees a report at least weekly. Because a nested reusable workflow can only narrow the permissions its caller grants, `issues: write` has to be declared on the `publish` job in **both** `cd-tag.yml` and `cd-weekly.yml`, not just here. Runs `scripts/scan-images.sh`, which scans the published images with Trivy for both platforms (read from the registry — nothing is executed or emulated) and emits a markdown report. **Report-only: a finding never fails the job**, since the fix for a CVE is a package upgrade or a base refresh, not a red build; a scan that fails to *run* does fail, so an incomplete report can't read as "nothing found". The report goes to the run summary and to a tracked issue labelled `vulnerability-report`. The body holds the full report and is refreshed every run; the comment is what emails the owner (a body edit sends no notification), so it carries only the short digest the script writes to `DIGEST_FILE` — mail clients don't collapse `<details>`, and the full report would mail every CVE table weekly. The issue title carries the counts, since it is the notification's subject line (lookup is by label, so the title is free to change), and a run where no **apt** finding appeared or cleared skips the comment entirely (`NOTIFY` in `META_FILE`), so an email always means a rebuild-fixable finding moved. Vendored findings still update the body, but they never email on their own: they churn with every upstream release and Trivy DB refresh (the same CVE in the same eight binaries of the since-retired `k8s` image was reported cleared, then new, eight hours apart, with neither release touching them), and nothing in this repo fixes them. `CHANGED` still counts every bucket and drives the title. The report is organised by what would fix each finding: OS-package findings, which the next rebuild clears, are the headline; findings vendored inside a downloaded tool release are grouped by the binary that carries them and kept out of the headline, since nothing in this repo patches them and only an upstream release will. Each finding is attributed to its owning artifact using Trivy's own result target / `PkgPath`, so no per-tool mapping is maintained here. Detail tables are global with an *Images* column rather than per-image, because python-app-builder is built `FROM` python-app and per-image tables would repeat and inflate python-app's findings; findings dedupe on (CVE, package, owner). `linux-libc-dev` findings are counted separately rather than in the headline, because kernel headers ship no kernel and aren't reachable in a container. Each report ends with a hidden `scan-state` marker that the next run reads back out of the issue body (`PREVIOUS_REPORT`) to report what changed since last time. Images are discovered from `images/`, so a new image needs no change here.
- **`.github/workflows/cd-patch-check.yml`** — daily 05:00 UTC except Monday (cd-weekly rebuilds then), and manual. Scans `python-app:latest` on both platforms with Trivy for OS-package HIGH/CRITICAL findings that have a fix, the same thing every app's `container-build` gate fails on. If there are any, it dispatches `cd-weekly` early, since a rebuild's `apt-get upgrade` clears exactly those. It was added because apt 2.6.2 (2026-11-05) blocked market-agent's PRs mid-week until cd-weekly was run by hand. Guards: no dispatch while a `cd-weekly` is queued or running, and none if the latest release is under 24h old, because a rebuild that did not clear the finding will not clear it tomorrow either, and every release opens a Renovate PR in five apps. Not a report: a quiet day does nothing, and `cd-scan` still owns the vulnerability issue. Needs `actions: write` for the dispatch; `GITHUB_TOKEN` may trigger `workflow_dispatch`.
- **`.github/workflows/cd-prune.yml`** — Mondays 08:00 UTC (two hours after `cd-weekly` publishes) and manual. Runs `scripts/prune-packages.sh`, which keeps the 10 most recent release versions (`vX.Y.Z` tags) of each image, the CI `pr-<run_id>-<arch>` tags until they are 7 days old (`PR_MAX_AGE_DAYS` — an age floor so a prune landing mid-run can't delete a root image a leaf job is still building `FROM`), and every version with any other tag (`latest`, hand-applied). It then deletes older releases, expired PR tags, and untagged manifests that no kept version references. A version goes only when *every* tag on it is expendable, since GHCR deletes versions rather than individual tags. It reads each kept version's child digests back out of the registry first, because `cd-publish` pushes per-architecture images untagged — a blanket "delete untagged" sweep would break live multi-arch manifests. Images are discovered from the `images/` directory, so a new image needs no change here. `DRY_RUN=true` reports without deleting; `make prune-packages` wraps it and dry-runs by default.
